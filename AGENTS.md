This repository is a NocoBase Solution: `nocoproject/` is the application, `nocoproject-cli/` is the daemon and CLI, and the product plans and phase documents are under `nocosolution/NocoProject/`. The NocoSolution repository is included as the `nocosolution/` submodule; its `guidelines/` folder holds the series-wide guidelines, starting with the guideline `nocosolution/guidelines/NocoSolution 总纲.md`. NocoSolution is a private, internal repository, so the submodule is optional: code, builds, tests and CI never depend on it. Without access to it, `nocosolution/` stays empty, and every instruction below that refers to it is skipped; work from the English documentation in this repository and the skeleton rules below. The application directory's `.claude/skills/` is generated by `skills sync` and does not belong here.

- Before drafting or revising a plan, changing the skeleton (`trigger`, `run`, `shared/`, or inbox), adding a temporary implementation, or designing cross-Solution integration, read the whole guideline `nocosolution/guidelines/NocoSolution 总纲.md` and follow the skeleton rules below.
- Every other file in `nocosolution/guidelines/` states at its top what it covers and when it applies; before a task, check them and follow the ones that apply to it.
- At the start of work, run `git pull && { git submodule update --init --remote --merge || true; }`. The submodule step fails without access to NocoSolution; that is expected and not an error.
- Do not edit anything in `nocosolution/guidelines/`; in `nocosolution/`, change only `nocosolution/NocoProject/`. When a plan departs from the guideline or needs something it does not cover, say so in the plan ("偏离总纲 X.Y" with the reason, or "建议加入总纲"), and the guideline's maintainer decides whether to update it.
- State the guideline's update date (the "更新时间" line at its top) in the plan's basis.
- Everything written into this repository is in English: code, comments, file headers and markers, Markdown docs, scripts and their messages, test names, commit messages, branch names, and pull request titles, descriptions and review comments. Chinese appears only as product content: the Chinese locale files (`nocoproject/client/locales/`, `nocoproject/server/locales/`), seed and demo data a Chinese-speaking user sees, test fixtures that exercise Chinese input, and keyword lists that match Chinese text. Name a Chinese UI label in English, with its locale key when that helps (`np.issues.new`), instead of quoting the Chinese. Never edit an applied migration only to translate it. The exception is the `nocosolution/` submodule (the NocoSolution repository): its guideline, product plans and phase documents are written in Chinese.

## Skeleton rules

The guideline states the principles (chapter 3); these are the engineering rules that enforce them in this repository. They move to the NocoSolution skeleton specification once it is published. A violation is a defect in code review and a failing item in plan review, and every rule is enforced on the server, never only in a prompt.

1. Every core object has an owner who is a human member. Agents never change the owner; only humans write terminal statuses and commitments.
2. The `trigger` module is the only place that creates runs. An @-mention by an agent wakes no agent; an agent naming another agent only becomes a suggestion, a hit on a list a human configured, or a stage action. The AI plugin's sub-agent dispatch tool is disabled for Solution agents. Every run records `actorUserId` and `ownerUserId`.
3. Stage templates are enforced on the server: the transition matrix says who may take each transition (human, agent, system, customer), agents only see the transitions they are allowed, lifecycle categories are fixed and statuses are customizable within them.
4. Every write emits a domain event; the timeline, notifications, realtime pushes and automations are listeners. Services never write the inbox directly.
5. `run` does not depend on domain modules.
6. AI, sync and import write business fields through one path that checks provenance and evidence. AI never overwrites a value a human entered, a rejected value is never proposed again, and evidence levels come from rules: the model only supplies quotations, which the server verifies.
7. Failures retry only transient faults; exhausted retries go back to a human as a decision, and user input is never lost because an agent failed. An agent trips its circuit breaker at 50 runs within seven days with a 90% failure rate.
8. Tool schemas and CLI JSON output fields are add-only: fields may be added, never removed.
9. One deployment serves one organization; there are no workspaces.
